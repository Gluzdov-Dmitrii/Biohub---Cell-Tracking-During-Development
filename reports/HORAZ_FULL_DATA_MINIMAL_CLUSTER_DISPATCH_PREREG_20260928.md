# Horaz all199: minimal cluster dispatch and one-shot queue gate

Date: 2026-09-28. This is a narrow implementation preregistration under `reports/HORAZ_FULL_DATA_REFIT_E10_E20_PREREG_20260928.md` and its deadline addendum. No GPU request or Kaggle action is authorized by this file alone.

The old EXP236 launcher is fixed to 115+11 source movies, short three-hour blocks and an immediate `WAITING_RESOURCE` cancel only when the request reply arrives. A lost reply can leave an unlaunched waiting request that later acquires a GPU. A full-data E10 needs about nine hours and all199 records. Therefore a minimal Horaz-specific stage/dispatch adapter is necessary; no general queue/controller rewrite or layers of audit are planned.

Reuse the established EXP236 immutable stage/hash pattern, its exact-state `engine.py` checkpoint resume, `scripts/exp223_supervisor.py` process observation and release, and read-only `monitor_exp213_job.py` probe. Create separate immutable E10 and E20 plans, code/run namespaces and one-shot lease IDs. Keep the full resolved recipe with `epochs=50` byte-identical across both checkpoint states; set only the bounded invocation epoch end to 10 or 20. E10 stores `epoch_010.pt`, E20 resumes from the E10 complete `last.pt` after binding its SHA and keeps the immutable E10 snapshot in the parent run. Distinct output directories prevent overwrite.

Stage exact code/manifest on CPU and verify every remote byte, all199 image/GEFF IDs and positive labeled windows, source6bba duplicate map (including the two formerly omitted IDs), max_nodes and source/target tensors before any request. A failed gate freezes the attempt. Wait without a queued Horaz request until a fresh fair-queue snapshot shows a suitable unallocated A100, no foreign WAITING claim ahead, and physical `nvidia-smi` memory/utilization/compute PIDs idle. The currently running primary f1 must finish normally and its lease be verified released before the default launch path; no reserved but physically idle GPU may be used.

Immediately before the first mutation, persist an fsynced unique `request_intent.json` binding plan/code/manifest SHA, lease ID, token digest, resources, run path and hard timeout. Make **one** queue request. Launch only from a parsed exact `RESERVED` response plus a fresh identical live row and idle allocated GPU. If the reply is `WAITING_RESOURCE`, make at most one owned cancellation and prove `CANCELLED`, `gpus=[]`, `process=null` and absent run. If the reply is lost, malformed or a state races, stop before launch, preserve raw transport and reconcile exact live ID; never re-request with the same identity or release an observable process. Persist launch intent before starting the wrapper; let the existing supervisor bound and release it. Require terminal exit0, exact checkpoint, dead owned process/group/GPU PID and `RELEASED/gpus=[]` before E10 promotion or E20 resume.

Provisionally plan E10 hard cap no more than 12 hours and lease at least 30 minutes longer; recalibrate from the first full-data epoch and keep enough margin for clean Kaggle execution and guarded POST before 2026-09-29 23:59 UTC. E20 gets a separate bounded lease only if it can finish all gates before the deadline. No E20 decision uses E10 public LB. A failed or incomplete E10 block cannot be promoted as a checkpoint candidate; only exact-state epoch-boundary resume may continue it under a distinct preregistered attempt.
